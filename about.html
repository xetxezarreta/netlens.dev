About & conventions // read me first

netlens.dev is a static field guide to the wire formats that show up in packet captures, kernel code and late-night incident calls. The diagrams are meant to be read next to a hex dump, not instead of the RFC.

static no trackers RFC-cited works offline

What this is

Thirteen protocol pages — IPv4, ICMP, IPv6, TCP, UDP, DNS, DHCP, HTTP, TLS, QUIC, BGP, Ethernet and ARP — plus a cross-layer packet dissector. Each protocol page has an interactive bit or byte diagram, a field reference with RFC citations, and an encoder and decoder that work on actual bytes. Nothing is sent to a server; the URL and the browser are enough.

Every protocol page has a copy page link button that serializes the visible codec fields into the URL hash. A permalink restores the inputs; encoder panels rebuild their output, and the DNS, DHCP, UDP and dissector links also re-run their decoders. Every protocol and tool page can download a JSON snapshot of its fields and outputs; the packet dissector can also copy a BPF filter or a Scapy snippet for the frame on screen. Nothing is uploaded: the URL is the entire state.

The design borrows the density and keyboard-friendly feel of a systems reference: monospace type, dashed rules, compact tables, offsets visible everywhere. The content is deliberately narrower than a general-purpose protocol encyclopedia. These are the headers you inspect when something is broken.

For network engineers

Check a field offset, settle the units question, or paste a header from a capture without opening five PDFs.

For security researchers

See reserved bits, flag combinations, TLV length traps and the exact bytes a scan recipe sets.

For implementers

Use the encoders as a second opinion on layout and the decoders as a sanity check on a new parser.

For the 03:00 call

Search a field name, jump to the bit range, confirm the RFC clause. Then go back to the pcap.

Conventions

Bit numbering

Bit 0 is the most significant bit of the first octet. Diagrams are drawn left to right, MSB first. A field labelled bits 0–3 occupies the high nibble of the first byte; bits 4–7 occupies the low nibble. This is the convention used by RFC diagrams and most packet dissectors.

0bit 3

The octet 0xA4 is shown above as bits 0–7. The high nibble is 0xA, the low nibble is 0x4.

Offsets

Byte offsets count from the first byte of the structure being described. On the IPv4 page, offset 0 is the version/IHL octet — not the start of the Ethernet frame. If the decoder detects an Ethernet frame, it says so and shifts internally. Bit offsets are absolute within the structure and inclusive at both ends.

Byte order

Network byte order is big-endian for IPv4, ICMP, IPv6, TCP, UDP, DNS, DHCP, HTTP/2, TLS, QUIC and BGP. HTTP/1.1 is text. Bytes inside a field are always written in transmission order; only the interpretation of multi-byte integers changes.

Layer grouping

The site uses the TCP/IP model as its primary map, with exactly four layers: 1 Link, 2 Internet, 3 Transport and 4 Application. BGP, DNS, DHCP, HTTP and TLS are application protocols; QUIC provides transport and integrates TLS; TCP and UDP provide process-to-process delivery; IPv4, ICMP and IPv6 cover addressing and control; Ethernet and ARP cover the link. The stack path at the top of each protocol page shows the actual encapsulation instead of forcing a single layer. The homepage renders an interactive stack map: click a layer to filter the field sheets, or a protocol to open its page.

Hex and lengths

Hex bytes are displayed uppercase with spaces: 45 00 00 28. Inputs accept spaces, colons, dashes, newlines and 0x prefixes. Lengths are in bytes unless a field explicitly says “words” or “8-byte units”. When a field is variable, the diagram shows a nominal width and marks it with a dashed edge; the actual length is carried by a preceding length field or by the packet boundary.

What the encoders do not do

The encoders build structurally valid bytes and compute Internet checksums where the page says so. They do not encrypt, authenticate, sign, compress payloads, fragment, route, or negotiate capabilities. DNS name compression and HPACK header compression are structural encodings, not content compression. A valid checksum is not a valid connection; a well-formed message with a bad authentication tag will be dropped by a real peer.

Keyboard

/Open the global field search from anywhere. Ctrl KSame search dialog (use ⌘ K on macOS). ↑ ↓Move through search results. ↵Open the selected result. EscClose the search dialog or clear a pinned diagram field. TabMove through diagram fields and controls; diagrams are buttons.

The search index covers protocol names, field names, option kinds, RFC numbers and common abbreviations. It is a static array in assets/search-index.js; no query leaves the page.

Accuracy & limits

The cited RFC is the authority. Some protocols have later updates that change field semantics without changing the layout: IPv4 DSCP/ECN, ICMP extensions and deprecated message types, IPv6 extension-header rules, TCP timestamps and ECN, BGP four-octet AS numbers and extended messages, QUIC v2 and DATAGRAM. The notes point at the relevant updates, but they cannot replace the current document and its errata.

Decoders are intentionally strict in some places and permissive in others. They report what they can prove from the bytes — lengths, reserved bits, checksums, flag patterns — and mark what they cannot verify, such as a TCP checksum without a pseudo-header or an authentication tag without keys. A clean parse means “structurally plausible”, not “authentic”.

If a diagram and a real implementation disagree, the implementation may be buggy, the RFC may have an erratum, or the deployment may be using an extension. Check all three. This site is independent and not affiliated with the IETF.

Privacy & tech

No cookies, analytics, fonts from third parties or background requests. The only client-side storage is a theme preference in localStorage. The typeface is JetBrains Mono (SIL Open Font License); the license text is in fonts/OFL.txt. Everything else is hand-written HTML, CSS and JavaScript. External RFC links open only when you click them.

For bug reports, corrections and feature requests, open an issue on GitHub. For private or security-related reports, email contact@netlens.dev.
