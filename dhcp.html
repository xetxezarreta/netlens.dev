DHCPv4 is BOOTP plus options. A request goes from UDP/68 to UDP/67; a server reply goes from UDP/67 to UDP/68. The magic cookie at offset 236 marks the option area.

~/protocols/dhcp

DHCP // RFC 2131

DHCP gives a host an IPv4 address and the configuration that goes with it: routes, DNS servers, a lease lifetime and more. The packet is a BOOTP header followed by a magic cookie and a list of type-length-value options.

01Message layout

BOOTP fixed header · magic cookie · options

Every DHCPv4 message starts with the 236-byte BOOTP header. The first four octets identify the operation and the client hardware address type; the next fields carry the transaction ID, timing, flags and four IPv4 addresses. A DHCP message then adds the magic cookie 63 82 53 63 and the option area.

The flags word

the fixed header is not the whole message

A DHCP message is at least 240 bytes once the magic cookie is present. The option area carries the message type, addresses, lease timers and every other parameter. A message with no option 53 is BOOTP-shaped but cannot identify itself as DHCP.

02Message types

option 53 · one byte · eight standard messages

The DHCP message type lives in option 53. It is one byte and must be present in every DHCP message. The standard exchange is DISCOVER → OFFER → REQUEST → ACK; NAK rejects a request, while RELEASE and DECLINE are client notifications.

DHCP is unauthenticated

Any host on the link can answer a DISCOVER. Rogue DHCP servers, spoofed ACKs and malicious option 82 data are operational security problems. DHCP snooping, port security and trusted relay ports are network controls, not protocol features.

03Options

code · length · value · end

Options are one-byte code and one-byte length TLVs. Code 0 is a one-byte Pad; code 255 is a one-byte End. A zero-length option is valid only when the option definition allows it. Repeated options are concatenated in the order they appear (RFC 3396).

option overload and concatenation

When option 52 is present, the server may place additional options in the file field (bit 1), the sname field (bit 2), or both (bit 3). RFC 3396 allows a single option to be split across multiple occurrences; a decoder must concatenate the values in order before interpreting them.

04Encoder

BOOTP header · common options · arbitrary TLVs

Build a DHCP message with a valid BOOTP header, magic cookie and option area. The message type is always emitted as option 53. Common lease fields have dedicated inputs; everything else can be supplied as one code = value option per line.

DHCP parameters

RFC 2131 · RFC 2132

Options can use numeric codes or names such as subnet-mask, router, dns, requested-ip, parameter-request-list, client-id, relay-agent and classless-route. Duplicate code 53 is generated from the message-type selector.

06Wire notes

operational details that matter
DHCP is not authenticated

The transaction ID, client hardware address, server identifier and option 82 data are all claims. Use DHCP snooping, trusted relay ports and switch-port security to limit who can answer. A valid checksum proves only that the bytes survived the path.

  • Client and server ports are fixed. Clients use UDP/68 and servers use UDP/67. The first DISCOVER is broadcast because the client does not yet have an address.
  • xid is matching, not authentication. A 32-bit transaction ID lets a client discard unrelated replies. It does not prove that a reply came from a legitimate server.
  • The broadcast flag is a workaround. A client that cannot receive unicast before its address is configured sets 0x8000 and asks the server to broadcast the reply.
  • Lease timers are relative. Option 51 is the total lease. Options 58 and 59 are renewal (T1) and rebinding (T2) times. Servers should keep T1 < T2 < lease, but clients must tolerate unusual values.
  • Option overload is legal. When option 52 is set, options may continue in file, sname, or both. Parse those areas before declaring an option missing.
  • Repeated options are concatenated. RFC 3396 permits a long option to be split across multiple TLVs. Concatenate the values in order; do not keep only the first occurrence.
  • Relay agent information is link metadata. Option 82 is added by a relay. A server must treat it as untrusted unless the relay is trusted, and the circuit-id format is deployment-specific.
  • DHCPv6 is a different protocol. DHCPv6 uses UDP/546 and UDP/547, different message types and options, and RFC 8415. Do not parse DHCPv6 with a DHCPv4 decoder.
