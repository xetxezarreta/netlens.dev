WireGuard messages // protocol v1

Four message types, fixed handshake sizes, little-endian indices and no version field. The handshake messages are mostly opaque cryptographic material; the transport message is where the counters and encrypted payload live.

01Message types

first 4 bytes · type + reserved

Every WireGuard message starts with an 8-bit Type and 24 reserved bits that must be zero. The four types have different sizes and different cryptographic contents. Integers after the header are little-endian, unlike almost every other protocol on this site.

1Handshake Initiation148 BInitiator sends ephemeral key, encrypted static key, timestamp, MACs.Sender Index; MAC1/MAC2.

the fields are encrypted, not just opaque

The encrypted static key, timestamp, empty payload and cookie are AEAD ciphertexts with 16-byte tags. MAC1 and MAC2 are keyed BLAKE2s values, not encryption. You cannot verify or produce them without the relevant keys and the receiver's public key.

02Transport data

type 4 · the steady state

After the handshake, transport messages carry encrypted IP packets. The header is 16 bytes: type, reserved, receiver index and a 64-bit little-endian counter. The rest is AEAD ciphertext, ending with a 16-byte authentication tag.

The counter is the AEAD nonce. Reusing a counter with the same key is catastrophic; receivers enforce an anti-replay window. The plaintext is padded to a multiple of 16 bytes (up to the MTU) before encryption.

03Endianness

little-endian integers · every time

WireGuard writes its integer fields little-endian. A sender index of 0x0a0b0c0d appears on the wire as 0d 0c 0b 0a. Reading it big-endian yields 0x0d0c0b0a — a different peer, or no peer at all.

The counter is not a sequence number visible to the IP layer; it is the AEAD nonce for the transport key. The receiver tracks the highest accepted value and a replay window.

06Wire notes

what the whitepaper does not put in a diagram
no RFC, but a precise specification

WireGuard is specified at wireguard.com/protocol and in the accompanying whitepaper. There is no IETF RFC for the core protocol. The message layouts are stable and deliberately small.

  • All integers are little-endian. Message type is a byte, reserved is three bytes, indices are 32-bit LE, the transport counter is 64-bit LE.
  • Reserved bytes must be zero. Receivers should discard a message with non-zero reserved bytes; they are not an extension point in protocol v1.
  • Handshake sizes are fixed. Initiation 148, response 92, cookie 64. A shorter or longer message is malformed, not an opportunity to guess.
  • Transport data has no MAC1/MAC2. Integrity is provided by the AEAD tag inside the encrypted payload. The header is associated data, not encrypted.
  • MAC1 is receiver-specific. It is keyed by a hash of the receiver's static public key; MAC2 is keyed by the cookie. They mitigate off-path floods but do not authenticate the peer.
  • Cookie replies are not session messages. They are a stateless DoS defense; the cookie is encrypted with a key derived from the source address and the challenged MAC1.
  • Padding is deliberate. The plaintext is padded to a multiple of 16 bytes; the receiver must not assume the IP packet fills the ciphertext.
