WireGuard // Noise handshake on UDP

WireGuard is a compact VPN protocol built on the Noise protocol framework. Four message types define the protocol: two handshake messages, a cookie reply for load mitigation and the transport-data message. There are no options, no cipher negotiation and no version field beyond the message type.

01Message types

4-byte little-endian type

The first 32 bits are a little-endian message type. The low byte is 1–4; the other three bytes are reserved and must be zero. Unlike TLS, there is no record layer and no plaintext alert channel. A malformed message is discarded.

This page is structural, not a crypto implementation

The codec reads the fields and lengths. It does not perform X25519, ChaCha20-Poly1305, BLAKE2s, MAC1/MAC2 verification or key derivation. A “valid” parse means the bytes match the message shape, not that the peer is authenticated.

02Handshake

initiation · response · cookie

The handshake is a Noise IKpsk2 exchange. The initiator knows the responder's static public key; the responder learns the initiator's static key from the encrypted field. The ephemeral keys provide forward secrecy. A cookie reply is a stateless proof-of-address mechanism, not a session message.

03Transport data

the message type most frequently observed

Transport data is 16 bytes of header followed by ciphertext. The 64-bit counter is little-endian, starts at zero for each key and must never repeat under the same key. The first 16 bytes of the encrypted payload are the Poly1305 tag; the inner packet follows. Without keys the inner IPv4/IPv6 packet is opaque.

The receiver index is not an IP address

It is a local handle the receiver chose for this session. It changes when the session is rekeyed and is not routable. It should not be mapped to a peer without the WireGuard state.

06Wire notes

design characteristics
  • No cipher negotiation. The protocol fixes Curve25519, ChaCha20-Poly1305, BLAKE2s and HKDF. A capture cannot show a downgrade because there is nothing to downgrade to.
  • No version in the packet. The message type and the protocol itself are the version. A future incompatible design would need a different framing.
  • Stateless until authenticated. The responder does not keep per-initiator state before it validates the handshake, which is why cookie replies exist.
  • Roaming is a feature. The peer's source address can change; the session is identified by indices and keys, not by the outer 5-tuple.
  • Keepalives are empty transport packets. They are encrypted like any other transport message; the inner payload is zero length.
  • Capture visibility is limited. Endpoints, timing, sizes and indices are visible. Inner addresses, ports and payload are not visible without keys.
