HTTP/1.1 is text; HTTP/2 is binary. Both carry the same semantics, but the framing, header encoding and concurrency model are completely different.

~/protocols/http

HTTP // RFC 9110 · RFC 9113

HTTP is two protocols with one name. HTTP/1.1 puts a text start line, header fields, a blank line and a body on a TCP stream, with Content-Length or chunked framing. HTTP/2 replaces that with binary frames, stream IDs and HPACK-compressed header blocks. This page decodes both and shows where the request-smuggling bugs live.

01HTTP/1.1 message layout

start line · header fields · empty line · body

An HTTP/1.1 message is a start line, zero or more header fields, an empty line and an optional body. Lines end in CRLF; the empty line is exactly CRLF. The start line is a request line for requests and a status line for responses.

the body is framed, not self-describing

HTTP/1.1 does not put a length on the whole message. The receiver decides where the body ends from the request method, the status code, Content-Length, Transfer-Encoding: chunked, or connection close. Every framing disagreement between two parsers is a potential request-smuggling bug.

02Request line & status line

ASCII · space separated · CRLF terminated

The request line carries the method, target and protocol version. The status line carries the version, a three-digit status code and a reason phrase. The reason phrase is informative only; clients must use the code.

03Body framing

Content-Length · chunked · close-delimited

Framing is the part of HTTP/1.1 that most often breaks in the real world. A response with both Content-Length and Transfer-Encoding: chunked is invalid enough that RFC 9112 says the message ought to be treated as an error; a proxy that prefers the other header is how request smuggling starts.

FramingBody ends whenUsed byRisk

Transfer-Encoding beats Content-Length

When both are present, a message with Transfer-Encoding: chunked uses chunked framing. A front-end that honours Content-Length while a back-end honours chunked can be made to see two different requests on one connection. Reject messages that carry both, and reject duplicate or non-identical lengths.

04HTTP/2 frames

9-byte header · multiplexed streams · binary

HTTP/2 keeps the request/response semantics and replaces the text framing with a binary frame layer. Every frame starts with a 24-bit length, an 8-bit type, an 8-bit flags field and a 31-bit stream identifier. A connection carries many streams at once, and header blocks are compressed with HPACK.

stream 0 is the connection

SETTINGS, PING and GOAWAY use stream 0 and apply to the whole connection. Streams are initiated with odd IDs by the client and even IDs by the server. A frame that appears on the wrong stream, or a DATA frame on stream 0, is a connection error, not a warning.

05HPACK header compression

static table · dynamic table · Huffman strings

HPACK is a stateful compression format shared by every stream on an HTTP/2 connection. Header fields are either indexed into a 61-entry static table, indexed into a dynamic table that both peers update in lock-step, or sent as literals. Strings may be Huffman coded. A decoder that loses state cannot recover until the connection ends.

Huffman is not encryption

HPACK Huffman coding is a fixed prefix code from RFC 7541. It makes header blocks smaller, not secret. The full 257-symbol table is implemented in this page's decoder; a block can mix Huffman and raw strings freely.

dynamic table size is a connection property

Each entry costs name length + value length + 32 bytes. The peer may announce a smaller SETTINGS_HEADER_TABLE_SIZE, and the encoder must emit a dynamic table size update before using the new size. Eviction is from the oldest entry. If you start decoding in the middle of a connection, indexed fields may refer to entries you never saw.

08Wire notes

what changes between HTTP/1.1, HTTP/2 and HTTP/3
HTTP semantics are stable; framing is not

Methods, status codes and header field semantics come from RFC 9110 and apply to HTTP/1.1, HTTP/2 and HTTP/3. The start line, header encoding, multiplexing and flow control are version-specific. A tool that only understands text HTTP will misread every HTTP/2 connection.

  • HTTP/2 headers must be lowercase. Field names containing uppercase letters are malformed. Pseudo-headers (:method, :path, :scheme, :authority, :status) come before regular fields.
  • Connection-specific headers are forbidden in HTTP/2. Connection, Keep-Alive, Proxy-Connection, Transfer-Encoding and Upgrade must not appear. TE is allowed only with the value trailers.
  • HTTP/2 flow control is per stream and per connection. DATA frames consume window; WINDOW_UPDATE restores it. A zero increment is a protocol error.
  • HPACK state is per connection, not per stream. HEADERS and CONTINUATION on different streams share one dynamic table. Starting a decode mid-connection can make indexed fields unresolvable.
  • Request smuggling lives in framing disagreement. Duplicate Content-Length, both Content-Length and chunked, whitespace before a colon, and obs-fold are all parser-differential bugs. Reject ambiguous messages.
  • Trailers are real headers. In chunked HTTP/1.1 they follow the zero chunk; in HTTP/2 they are a HEADERS frame after DATA with END_STREAM. Do not drop them silently.
  • HTTP/3 is HTTP over QUIC. Requests and responses run on QUIC streams, and header compression is QPACK rather than HPACK. There is no TCP head-of-line blocking, but stream-level flow control and QUIC loss recovery replace it.
  • HTTPS is HTTP inside TLS. ALPN selects h2 or http/1.1. The HTTP bytes only become visible after the TLS handshake and record decryption.
