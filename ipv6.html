IPv6 // RFC 8200

A fixed 40-byte header, 128-bit addresses and a next-header chain that replaces IPv4 options. IPv6 dropped the header checksum, moved fragmentation to the source and separated routing, fragment and destination options into extension headers. The result is simpler to forward and harder to parse blindly.

01Header layout

fixed 40 bytes · no options in the base header

The IPv6 header is always 40 bytes. The first 32 bits pack Version, Traffic Class and Flow Label; then come Payload Length, Next Header, Hop Limit, and the 128-bit source and destination addresses. There is no IHL, no header checksum and no base-header options field.

Payload Length is not the frame length

Payload Length counts everything after the 40-byte base header: extension headers plus the upper-layer payload. It does not include the base header and it does not include Ethernet padding or FCS. A value of zero is valid for an empty packet, or for an RFC 2675 jumbogram when a Hop-by-Hop Jumbo Payload option is present.

02Traffic class & flow label

the first 32 bits, packed

Version, Traffic Class and Flow Label share the first 32 bits. Traffic Class is the same DSCP/ECN octet used by IPv4 Differentiated Services; Flow Label is a separate 20-bit identifier intended for flow classification and load balancing. It is not a port and it does not identify a connection.

The high nibble is the version (6). The next 8 bits are DSCP (6 bits) plus ECN (2 bits). The low 20 bits are the flow label. A flow label of zero means “no label”; routers must not change a non-zero label.

03Addresses

128 bits · RFC 5952 text form

An IPv6 address is 128 bits, written as eight 16-bit hexadecimal groups. Leading zeros in a group are removed and the longest run of zero groups is compressed with ::. Only one :: is allowed. The wire format is always the full 16 bytes; the shortened text form is only a display convention.

zone identifiers are local syntax

fe80::1%eth0 tells the local stack which interface to use. The %eth0 part is not encoded in the IPv6 header and does not travel across the wire. It is scope information, not an address field.

04Extension headers

the next-header chain

IPv6 moves optional processing into separate extension headers. Each one starts with a Next Header byte and a length field, then type-specific data. Only Hop-by-Hop must be first; the usual order is Hop-by-Hop, Destination Options, Routing, Fragment, AH, ESP, a final Destination Options header, then the upper-layer protocol.

the chain is not free-form

Only Hop-by-Hop must appear first, but routers and firewalls commonly enforce the recommended order and may drop unexpected combinations. IPv6 fragmentation is performed by the source, not by routers; a fragment header with offset 0 and M=0 is an atomic fragment. AH and ESP change the length accounting and the visibility of the upper layer.

05Encoder

base header · payload length auto

Build a structurally valid IPv6 base header and append a payload. Payload Length is calculated from the bytes you supply, so it includes any extension headers you paste or generate. The optional presets create a TCP, UDP, ICMPv6, Hop-by-Hop or Fragment example; transport checksums are calculated for the current source and destination when a preset is loaded.

The base header has no checksum. Transport checksums use an IPv6 pseudo-header: source, destination, upper-layer length and next header. If you edit addresses after loading a preset, the preset checksum is no longer valid for the new addresses.

06Decoder

IPv6 packet or Ethernet frame

Paste a raw IPv6 packet or an Ethernet II frame with EtherType 0x86DD. The decoder follows the Next Header chain through Hop-by-Hop, Routing, Fragment, AH and Destination Options headers, reports each length and offset, and stops at the first upper-layer protocol. It also detects RFC 2675 Jumbo Payload options.

07Wire notes

what changed from IPv4
no header checksum

IPv6 removed the per-hop header checksum. Link layers and upper layers detect errors; TCP, UDP and ICMPv6 checksums include an IPv6 pseudo-header. This means a router can decrement Hop Limit without recomputing a header checksum, but it also means a corrupted base header may not be detected until the upper layer.

  • Payload Length includes extension headers. It is not the length of the upper-layer payload alone. Subtract the chain lengths to find the transport payload. A zero value is meaningful: empty packet or jumbogram with a Jumbo Payload option.
  • Hop Limit is not TTL. It counts hops, not seconds, and is decremented on every forwarding router. Initial values are convention, not protocol constants. Zero produces ICMPv6 Time Exceeded.
  • Fragmentation belongs to the source. IPv6 routers do not fragment packets; they send ICMPv6 Packet Too Big when the packet exceeds the path MTU. The Fragment header uses a 32-bit identification and an offset in 8-byte units.
  • Address text is not wire format. The wire is always 16 bytes. RFC 5952 canonical text compresses the longest zero run, lowercases hex and omits leading zeros. Zone identifiers such as %eth0 are local scope syntax.
  • No broadcast. IPv6 uses multicast and anycast. All-nodes multicast is ff02::1; solicited-node multicast is ff02::1:ff00:0/104. ARP is replaced by Neighbor Discovery over ICMPv6.
  • Extension chains need limits. A parser must bound the number of extension headers it follows, validate every length before slicing, and stop at ESP because the next header is encrypted.
  • Filtering ICMPv6 breaks IPv6. Neighbor Discovery, Router Advertisement, Packet Too Big and Time Exceeded are not optional noise. Blanket ICMP drop policies are a common cause of IPv6 black holes.
  • Extension headers are not IPv4 options. They are chained through Next Header values and counted in Payload Length; AH uses 4-octet length units, while Hop-by-Hop, Routing and Destination Options use 8-octet units.
