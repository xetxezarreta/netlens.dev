02How the walk works

each layer names the next one

A dissector does not guess the whole stack at once. Each header carries the identifier needed to find the next header. Ethernet has an EtherType, IPv4 has a Protocol byte, IPv6 has a Next Header chain, and TCP/UDP have ports that suggest an application protocol. The walk stops when a layer has no decoder, when a length check fails, or when a fragment does not contain the transport header.

ports are hints, not proof

A UDP datagram to port 53 is usually DNS, but nothing in UDP enforces that. The dissector tries the application decoder only when the payload parses; otherwise it shows an opaque payload layer. Unknown protocols are a normal result, not a failure.

03Limits & safety

what this tool deliberately does not do
  • No decryption. TLS application data (including HTTP inside HTTPS), QUIC protected packets, ESP and encrypted BGP sessions remain opaque.
  • No IP reassembly. A non-initial IPv4 or IPv6 fragment has no transport header. The dissector marks fragment data and stops instead of inventing a payload.
  • No TCP stream reassembly. One TCP segment is one input. A DNS message split across segments needs a stream reassembler, not a single-frame dissector.
  • No pcap import. The input is hex bytes. Extract one packet from your capture tool, or use the protocol pages for a specific header.
  • No checksum enforcement. Invalid checksums are reported as warnings. Offloaded NICs often emit frames before the checksum is filled in, so a capture can legitimately show a bad value.
  • Every parse is bounded. Pointer chains, extension-header chains and record counts all have guards, so malformed input produces warnings rather than an infinite loop.
captures can be hostile

Treat pasted bytes as untrusted input. This page never executes payloads, never dereferences pointers outside the buffer, and never makes a network request. It also does not prove that a frame was valid on the wire; it only shows what its bytes say.
