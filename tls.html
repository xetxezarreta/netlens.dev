TLS is a record protocol. Handshakes, alerts and application bytes are all carried inside typed records. TLS 1.3 encrypts everything after ServerHello.

~/protocols/tls

TLS 1.3 // RFC 8446

TLS wraps every byte after a TCP connection in a typed record. Inside those records, ClientHello and ServerHello negotiate a version, cipher suite, key share and ALPN protocol; extensions carry SNI, groups, signatures and certificates. This page decodes the plaintext handshake and the record layer, and shows exactly where the encrypted boundary begins.

01Record layer

five-byte header · typed fragments

TLS does not hand TCP a naked handshake message. Every message is first wrapped in a record: one content type, a legacy version, a two-byte length and the fragment. A handshake message may span several records, and one record may hold several handshake messages. The record layer is also where AEAD protection is applied.

Content typeCodeFragmentTLS 1.3 note
ChangeCipherSpec201 byte, value 0x01Compatibility only. It is not a key change in TLS 1.3.
Alert21Level + descriptionFatal alerts close the connection. Some alerts are encrypted.
Handshake22One or more handshake messagesPlaintext only until ServerHello; later handshake records are encrypted inside application data.
Application Data23AEAD-protected bytesAlso carries encrypted handshake messages after ServerHello.
Heartbeat24Heartbeat messageRarely used; historically a source of memory-disclosure bugs.
the legacy version is not the negotiated version

TLS 1.3 records use 0x0303 in the legacy record version for compatibility, and the initial ClientHello record may use 0x0301. The real version is negotiated in the supported_versions extension. Do not infer TLS 1.3 from the record header alone.

02Handshake messages

one type byte · three length bytes

Every handshake message begins with a one-byte type and a 24-bit length. The length counts the body only, so the total message is 4 + length bytes. Handshake messages are ordered: the client speaks first, the server answers, and Finished proves that both sides derived the same keys.

TypeNameDirectionPurpose
1ClientHelloC → SVersion, random, session ID, cipher suites, key share and extensions.

4NewSessionTicketS → CResumption lifetime, nonce, ticket and early-data size.
5EndOfEarlyDataC → SMarks the end of 0-RTT data.

11CertificateS → C / C → SCertificate chain and per-certificate extensions.
13CertificateRequestS → CRequest for client authentication.

20FinishedBothHMAC over the transcript with the finished key.
24KeyUpdateBothRequests a new application traffic secret.
the encrypted boundary

In TLS 1.3 only ClientHello and ServerHello are plaintext handshake messages. Everything after ServerHello — EncryptedExtensions, Certificate, CertificateVerify and Finished — is sent as Application Data records protected with handshake traffic keys. A capture without keys shows ciphertext, not a parseable Certificate message.

04ClientHello & ServerHello

the two plaintext messages worth knowing by heart

The hello messages carry the negotiation. ClientHello lists what the client supports; ServerHello selects one version, one cipher suite and one key share. Both keep the TLS 1.2 field shapes so middleboxes see a familiar structure, then move the real decisions into extensions.

05Extensions

type · length · data · repeated everywhere

Extensions are the extension mechanism that made TLS 1.3 possible without changing the hello envelope. Each one is a four-byte header and an opaque body whose shape depends on the extension type and the message that carries it. The same type can mean different things in ClientHello, ServerHello, EncryptedExtensions and Certificate.

06TLS 1.3 key schedule

HKDF-Extract · Derive-Secret · Expand-Label

TLS 1.3 replaces the TLS 1.2 PRF cascade with a small HKDF-based schedule. Two inputs matter: the ECDHE shared secret and the PSK (zero when there is no resumption). Each stage mixes in a transcript hash, so a change to any handshake byte changes every later traffic secret.

AEAD nonce construction

TLS 1.3 builds the per-record nonce by XORing the 64-bit record sequence number into the static IV derived from the traffic secret. The sequence number resets to zero when keys change. Reusing a nonce with the same key breaks AEAD catastrophically, which is why KeyUpdate exists and why the record sequence number must never wrap.

07Alerts

two bytes · level and description

An alert is a two-byte record fragment. The level is 1 for warning or 2 for fatal. In TLS 1.3 most alerts are fatal, and alerts sent after the handshake keys are installed are encrypted like application data.

08Encoder

what the encoder does not do

It does not generate a private key, sign the transcript, derive traffic keys or encrypt anything. It builds the plaintext record and handshake structures so you can inspect the layout and feed the bytes to a decoder.

10Wire notes

what TLS 1.3 removed, and what still bites
TLS 1.3 is not “TLS 1.2 with a new version number”

RSA key transport, static DH, CBC-mode suites, compression, renegotiation and custom DHE groups are gone from TLS 1.3. A ClientHello that offers only 0x0303 is a TLS 1.2 client even if the record layer looks modern.

  • SNI is not authentication. The server_name extension selects a certificate; the certificate and CertificateVerify signature are what prove the endpoint.
  • ALPN is negotiated, not implied by the port. TCP/443 can carry HTTP/1.1, HTTP/2 or another protocol. Read the ALPN result in EncryptedExtensions before assuming HTTP/2.
  • 0-RTT is replayable. Early data is encrypted with keys derived before the handshake completes. Servers must restrict it to idempotent operations.
  • Record boundaries are not message boundaries. A single handshake message can span records, and one record can contain several handshake messages. A decoder must buffer across records.
  • Encrypted records reveal lengths. TLS 1.3 hides content but not record sizes or timing. Padding and record_size_limit reduce, but do not remove, traffic analysis.
  • The certificate chain can be large. A Certificate message may exceed one record; the decoder concatenates handshake fragments before parsing.
  • Middlebox compatibility mode. Many TLS 1.3 clients send a non-empty legacy_session_id and a dummy ChangeCipherSpec record so older middleboxes keep working. Neither changes the keys.
  • DoT, DoH and DoQ are different transports. DoT is TLS over TCP/853, DoH is HTTP over TLS, and DoQ is QUIC. The TLS handshake is similar; the framing above it is not.
