UDP // RFC 768

The minimal transport protocol: two ports, a length and a checksum. UDP adds multiplexing and error detection, then gets out of the way. It is the substrate for DNS, DHCP, NTP, QUIC, WireGuard and most of the traffic that would rather have low latency than a handshake.

01Datagram layout

eight bytes of header · then payload

A UDP datagram is an 8-byte header followed by data. Source Port and Destination Port identify the sending and receiving endpoints; Length counts the header plus data; Checksum covers a pseudo-header, the UDP header and the data. The IP layer supplies the source and destination addresses used by the pseudo-header.

Length includes the header

A UDP datagram with no payload has Length = 8. The maximum is 65535, and the data field is therefore at most 65527 bytes before IP-level limits. The IP payload may be larger than the UDP Length only if there is trailing data, which is malformed for ordinary UDP.

02Ports & services

16-bit endpoints · 0–65535

A UDP connection is really a four-tuple: source address, source port, destination address and destination port. The first 1023 ports are system or well-known ports; 1024–49151 are user/registered ports; 49152–65535 are dynamic or private ports. The source port is often ephemeral, while the destination port names the service.

UDP is a reflection target

The source address is not authenticated. Any protocol that sends a large response to a spoofed source can be used for amplification. Rate limiting, response-size checks and ingress filtering are operational controls, not UDP features.

03Length & checksum

pseudo-header · IPv4 vs IPv6

The UDP checksum is the one's-complement sum of a pseudo-header, the UDP header and the UDP data. The pseudo-header binds the datagram to its IP source and destination so a misdelivered packet is rejected. IPv4 makes the checksum optional: a transmitted zero means “no checksum.” IPv6 makes it mandatory, and a zero checksum is invalid.

ContextPseudo-headerChecksum ruleReference
IPv4Source 4 B + destination 4 B + zero 1 B + protocol 1 B (17) + UDP Length 2 B = 12 BOptional. A checksum field of zero means the sender did not compute one. A computed zero is transmitted as 0xFFFF.RFC 768 · RFC 1071
IPv6Source 16 B + destination 16 B + UDP Length 4 B + three zero bytes + next header 1 B (17) = 40 BMandatory. Zero is invalid; a computed zero is transmitted as 0xFFFF.RFC 8200 §8.1
the checksum is not a MAC

A valid UDP checksum proves that the pseudo-header, header and payload survived the path without accidental corruption under the sender's computation. It does not prove who sent the datagram, and NAT devices may need to rewrite it when they change addresses or ports.

04Encoder

length auto · checksum with IP context

Build a UDP datagram and compute its checksum with an IPv4 or IPv6 pseudo-header. The output can be the raw UDP datagram or a complete IP packet. The source and destination addresses are context, not UDP header fields; they matter only for the checksum and the optional wrapper.

06Wire notes

minimal by design
UDP is a multiplexing layer, not a reliable transport

UDP provides ports and an optional checksum. It does not provide connection setup, sequencing, retransmission, flow control or congestion control. Applications that need reliability build it above UDP, as QUIC does, or use TCP instead.

  • Length counts the header. A zero-payload datagram has Length 8. If the IP payload is longer than the UDP Length, the extra bytes are not part of the UDP datagram; ordinary UDP should not include them.
  • The checksum includes a pseudo-header. IPv4 uses a 12-byte pseudo-header; IPv6 uses 40 bytes. The UDP Length field participates, so rewriting lengths without updating the checksum breaks it.
  • Zero checksum is context-dependent. In IPv4 it means “not computed.” In IPv6 it is invalid. A computed checksum of zero is transmitted as 0xFFFF.
  • NAT rewrites checksums. A NAT that changes an address or port must recompute the UDP checksum. Captures taken at different points on the path can legitimately disagree.
  • Fragmentation is an IP concern. UDP has no fragment fields. IPv4 may fragment at routers; IPv6 uses a Fragment extension header and source-based fragmentation. A decoder needs the first fragment to see the UDP header.
  • Port numbers are not authentication. A source port is a claim, not an identity. UDP reflection and spoofing are common because there is no handshake.
  • UDP-Lite is different. UDP-Lite changes the length field semantics and allows partial checksum coverage. It uses IP protocol 136, not UDP protocol 17; do not parse it with a UDP assumption.
